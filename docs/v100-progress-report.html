YuE2 在 V100 上的推理適配與訓練驗證

原模型已在單張 V100 上生成完整歌曲，聽感和 A100 上的結果接近。訓練迴圈也已驗證可以計算損失、反傳、另存權重並重新生成。這 5 步權重更新聽不出明顯差別，因此不把它當作新基模。

結論

  • 基模是 /cache/yue2_files/YuE2-3B，解碼器是 /cache/yue2_files/YuE2-Vae。續訓從這份 checkpoint 開始，不從頭訓練。
  • 可用環境是現有的 PyTorch-2.0.0：Python 3.9.11、torch 2.3.1+cu121。不要升級到 torch 2.10 的 CUDA 12.8 輪子。
  • 機器是 8 張 Tesla V100-PCIE-32GB，驅動 535.183.01，最高 CUDA 12.2。官方 torch 2.10 需要約 570 的驅動，目前載入不了。
  • 官方語義 tokenizer 沒有發布。現在不能用新錄音做論文裡那套完整監督。

已完成的工作

項目結果
硬件確認8 張空閒的 V100 32GB。驅動 535 只支援到 CUDA 12.2。
環境選擇conda 建新環境被代理擋住，直接連 PyPI 失敗。改用已能看見 GPU 的 PyTorch-2.0.0，沒有更換 torch。
V100 代碼適配torch 2.3 沒有 is_flash_attention_available 和 enable_gqa。缺少時展開 KV 頭，改走普通注意力。新版 torch 的原行為保持不變。
推理跑通同一套 eager 路徑生成 58.9 秒音頻，耗時 125.8 秒。樂譜 513 token，語義 1474 token。聽感和 A100 接近。
輸出位置省略輸出參數時寫到 /cache/yue2_outputs/<歌曲 id>/。保留 FLAC，並在有 ffmpeg 時另存 MP3。
損失與反傳用已生成歌曲的 token 計算自迴歸損失。707 token 中 65 個被監督，ar_loss=3.6250，梯度有限。權重未改。
小步續訓與再生成只更新輸出層 5 步，另存到 /cache/yue2_ckpts/lmhead-city-lights。損失降到 3.6094 後停住。用新權重又生成 60.8 秒音頻和 MP3。聽起來與原版差異不大。

目前固定的推理配方

單卡、eager、不升級 torch。權重與 VAE 用本地目錄。BF16 在 V100 上由 FP32 模擬，一首約一分鐘的歌大約兩分鐘算完。

CUDA_VISIBLE_DEVICES=0 PYTHONPATH=src python -m yue2.cli generate --request examples/song.json --model /cache/yue2_files/YuE2-3B --vae /cache/yue2_files/YuE2-Vae --offline --device cuda --backend torch-eager --budget 30

訓練驗證說明了什麼

3.625 的交叉熵是原模型在自己生成的 token 上的分數。184704 類完全隨機時約為 12.1，所以它只說明原模型認得這些 token，不是音質指標。5 步輸出層更新只讓損失下降 0.016，聽感也幾乎不變。這證明存檔、重新載入和再生成是通的，不證明模型變好。

/cache/yue2_ckpts/lmhead-city-lights 只記住了 65 個 token，到此停止。以後續訓仍從 /cache/yue2_files/YuE2-3B 開始，結果另存。全參 Adam 狀態放不進 32GB。

下一步

  1. 不再給這份輸出層權重加步數，也不把它當新基模。
  2. 用 4 到 8 條固定提示詞和 seed，在原模型上做聽感對照。每張 V100 跑一個獨立進程。各次結果放進 /cache/yue2_outputs/ 的不同子目錄。
  3. 對照內容先選推理可控的設定：cot=full、cot=off，以及改 ABC 之後再渲染。先不增加訓練步數。
  4. 有新的歌曲數據之後，再從 YuE2-3B 做小範圍 AR 續訓。每次只改一種設定，並和原模型的同一批歌對聽。訓練後若變差，就停。
  5. 語義 tokenizer 出現之前，不用新錄音冒充完整的樂譜、語義 token 和 latent 監督。VAE 繼續凍結。

  • 不把 A100 上的 .venv-yue2 整份複製過來運行。那是 Python 3.12.11 加 torch 2.10.0+cu128。
  • 不用 8 張 V100 從頭復現論文的 64 張 H800 訓練。
